## 1. Стек: React + TypeScript + Vite, без игрового движка

Для «Словополя» игровой движок не нужен. Словесная игра — это текст, списки, кнопки, модальные окна и клавиатурный ввод. Это ровно то, что DOM и React делают лучше всего, и ровно то, в чём у вас уже есть опыт. Canvas-движок (Phaser) понадобился бы для спрайтов, физики и анимационного геймплея — этого здесь нет.

### Сравнение вариантов

| Критерий | React/DOM (выбрано) | Phaser 3 (движок) |
|---|---|---|
| Кривая входа для веб-разработчика | Нулевая | 2–4 недели на освоение |
| Текстовый UI (слова, списки, модалки) | Родной, доступный, чёткий | Костыльный (canvas-текст) |
| Клавиатурный ввод и автокоррекция | Тривиально | Сложнее |
| Скорость до первого билда | Быстрее в 1.5–2 раза | Медленнее |
| Вес бандла | ~100–300 КБ кода + SDK | +1–1.5 МБ движка |
| Анимации карты | CSS-переходы достаточно | Избыточно |
| Переиспользование в «Дачном Сезоне» | Нет | Да — но тот проект лучше начать после первого релиза |

### Что это значит на практике

- Экран игры: колесо букв как DOM-элементы, ввод — кнопками и клавиатурой, проверка слова — чистая функция.
- Карта путешествия: вертикально скроллящийся контейнер + SVG-маршрутная линия + кружки остановок. Никакого canvas.
- Анимации: CSS transitions (появление слова, подскок очков). Библиотеки анимаций на v1 не нужны.
- SDK Яндекса — обычный JavaScript, совместим с чем угодно. Phaser его тоже просто обёртывает — то есть выбор «без движка» ничего не блокирует.

**Когда учить Phaser:** на «Дачном Сезоне» (idle-merger требует спрайтов и анимаций). Это осознанная инвестиция во второй проект, и учить его будет проще, когда вы уже пройдёте один полный цикл на знакомой технологии.

## 2. ИИ-стратегия: какие модели для каких задач

### 2.1 Принцип «один сильный + много дешёвых»

Не платите за то, что бесплатные модели делают одинаково: рутинные правки, переименования, шаблонный код, документацию, простые скрипты. Платная подписка нужна там, где цена ошибки высока: архитектура, гейм-дизайн, генерация словаря, ревью сложных решений. При 10–20 ч/нед одного сильного ассистента хватает с запасом.

Бесплатные модели остаются на всю рутину. Если к моменту покупки появятся новые тарифы — критерий выбора один: сильная модель + удобное подключение к OpenCode ≤ $10–20.

| **Арт** | Бесплатные генераторы | Фон карты, иконки (см. раздел 10) | Отдельные сервисы |

### 2.4 Рабочий процесс с OpenCode — 10 правил

1. **`/init` в первый же день.** OpenCode проанализирует проект и создаст `AGENTS.md`. Закоммитьте его — это постоянная память агента о проекте (шаблон — в 2.5).
2. **Plan перед Build.** Клавиша Tab переключает режимы. Любая задача крупнее одного файла — сначала план, потом код. С планом дешевле спорить, чем с кодом.
3. **Одна задача = одна сессия = один коммит.** «Добавить валидацию ввода» — да. «Сделать игру» — нет.
4. **`@файл` для контекста.** Указывайте конкретные файлы вместо описаний «где-то в проекте». Перетаскивайте скриншоты прямо в терминал — OpenCode их читает.
5. **`/undo` без стеснения.** Не понравился результат — откат и переформулировка, а не правка руками поверх кривого кода.
6. **Просите JSON со схемой** для любых данных (словарь, конфиги уровней). JSON проверяется скриптом, прозу — глазами.
7. **Никогда не вставляйте секреты** в промпты и не коммитьте ключи. Всё секретное — в переменных окружения, `.env` в `.gitignore`.
8. **Говорите с агентом как с джуниором:** контекст, пример, ожидаемый результат, ограничения. «Сделай красиво» — плохой промпт, «сделай экран X по макету на скриншоте, шрифт ≥18px, кнопки ≥48px» — хороший.
9. **Проверяйте диффы перед коммитом.** Бесплатные модели склонны к «творчеству» в чужих файлах — просите не трогать то, что не относится к задаче.
10. **Незнакомое — спрашивайте до кода.** «Объясни, как работает сохранение в SDK Яндекса» стоит копейки; переделка по неверной гипотезе — часы.

Все команды проверены под Ubuntu/Debian; для других дистрибутивов замените apt на свой пакетный менеджер.


nvm выбран (вместо системного пакета), потому что позволяет держать несколько версий и обновлять Node без sudo. Для Яндекс.Игр достаточно любого актуального LTS.

## 4. Яндекс.Игры: аккаунт, SDK и первый билд (один вечер, неделя 1)

### 4.1 Регистрация и черновик игры

1. Войдите Яндекс-аккаунтом на **yandex.ru/games/console** (Developer Console).
2. Заполните профиль разработчика: имя/студия, контактный email. Платёжные данные для выплат можно отложить, но лучше заполнить сразу — это несложно и снимет вопрос потом.
3. «Создать игру» → черновик. Заполните, что понятно (название «Словополь», категория — головоломки/слова), остальное дополните к неделе 8.
4. Ничего не отправляйте на модерацию — черновик позволяет тестировать игру до релиза.

### 4.2 Скачивание и подключение SDK

1. Откройте документацию: **yandex.ru/dev/games/doc/dg/** → раздел «SDK» (там же: реклама, покупки, сохранения, лидерборды).
2. Скачайте архив SDK, файл `sdk.js` положите в `public/`.
3. Подключите **до** загрузки модулей игры в `index.html`:

```html
<script src="/sdk.js"></script>
```

SDK экспортирует глобальный объект `YaGames`. Все вызовы платформы (реклама, сохранения, покупки) идут через него. Поскольку документация SDK периодически обновляется, точные сигнатуры методов сверяйте с актуальным разделом перед интеграцией — в плане ниже структура обёртки, а не копипаста API.

### 4.3 Обёртка + мок — ключевой приём для локальной разработки

Проблема: SDK полноценно работает только внутри iframe Яндекса — локально реклама, сохранения и авторизация не заработают. Решение: единый интерфейс с двумя реализациями — реальной и мок-версией для разработки.

```ts
// src/sdk/types.ts (сокращённо)
export interface GameSDK {
  ready(): void                                  // LoadingAPI: снять экран загрузки
  lang(): string                                 // 'ru' | 'en' | ...
  isMobile(): boolean
  getPlayerData(): Promise<Record<string, unknown> | null>
  setPlayerData(data: Record<string, unknown>): Promise<void>
  showFullscreenAd(): Promise<void>              // interstitial
  showRewardedAd(): Promise<boolean>             // true = награда выдана
  setScore(boardId: string, score: number): Promise<void>
  purchase(id: string): Promise<void>            // IAP (детали — в документации)
  hasPurchase(id: string): Promise<boolean>
}
```

- `src/sdk/real.ts` — вызывает `window.ysdk` (создаётся после `YaGames.init()`), каждый метод оборачивает в try/catch: **любой сбой SDK не должен ломать игру**, локальный fallback на localStorage.
- `src/sdk/mock.ts` — localStorage вместо облака, `setTimeout` 2–3 секунды вместо рекламы с `console.log('[MOCK AD] rewarded')`, всегда `lang() = 'ru'`.
- `src/sdk/index.ts` — выбор реализации:

```ts
import { mock } from './mock'
import { real } from './real'
export const sdk = import.meta.env.DEV ? mock : real
```

Плюс этого приёма: вся игра работает в поезде/офлайне, тесты не зависят от платформы, а переключение — одной строкой.

### 4.4 LoadingAPI ready

После инициализации обязательно вызовите готовность игры — платформа убирает свой экран загрузки только по этому сигналу:

```ts
YaGames.init().then((ysdk) => {
  window.ysdk = ysdk
  ysdk.features?.LoadingAPI?.ready()
})
```

Отсутствие `ready()` — типичная причина «игра висит на загрузке» и отклонения на модерации.

### 4.5 Первый деплой в черновик (цель недели 1)

```bash
bash scripts/package.sh
```

Developer Console → ваша игра → «Загрузить версию» → выберите zip → откройте черновик по ссылке. Проверьте:

- [ ] игра открывается в iframe и стартует за ~2–3 секунды;
- [ ] `ready()` сработал (нет вечного экрана загрузки);
- [ ] прогресс сохраняется и восстанавливается после перезагрузки страницы;
- [ ] в консоли браузера нет красных ошибок;
- [ ] игра выглядит нормально на телефоне (откройте черновик со смартфона).

## 5. Словарный пайплайн (ядро качества, недели 2 и 4)

В анализе рынка прямо сказано: качество RU-словаря — критический фактор успеха словесной игры. ИИ генерирует слова быстро, но **галлюцинирует**: может выдать несуществующее слово или имя собственное. Поэтому строим конвейер «генерация → машинная валидация → ручная выборочная проверка».

### 5.1 Правила игры (зафиксировать в GDD и AGENTS.md)

- Из 7 букв составляются все слова длиной от 3 до 7 букв.
- Только **существительные в именительном падеже единственного числа** (стандарт жанра: снимает споры о формах слов).
- Имена собственные — нельзя; уменьшительные («котик») — нельзя.
- Ё нормализуется в Е везде — и в данных, и во вводе игрока.
- На остановке: минимум 20 валидных слов, из них 2–3 «бонусных» редких.

### 5.2 Источник истины

Машинная проверка требует эталонного словаря. Два бесплатных варианта:

- **hunspell-ru** — `sudo apt install hunspell-ru`, файл `/usr/share/hunspell/ru_RU.dic`. Проверьте лицензию файла при поставке в бандле (обычно допустимо, но зафиксируйте источник).
- **Леммы OpenCorpora** (opencorpora.org) — открытый список словоформ, удобен тем, что сразу размечены части речи.

Скрипт нормализует обе стороны: lowercase, ё→е, обрезка пробелов.

### 5.3 Конвейер производства одной карты (30 остановок)

1. **Генерация:** промпт П12 (раздел 8) выдаёт по 5 наборов за раз в JSON. На карту — ~7–8 запросов.
2. **Валидация:** `node scripts/validate-dictionary.mjs` проверяет каждый набор (критерии — в 5.4). Отчёт: сколько наборов прошло, какие слова отсеяны и почему.
3. **Ручной ревью:** глазами просмотреть 10–15% прошедших наборов (там, где сомневались) и **весь список слов на нецензурную лексику** — это отдельный фильтр в скрипте.
4. **Сборка:** провалившиеся слова отбрасываются; если у набора осталось <20 слов — пометить на перегенерацию.

Реалистичная скорость: карта целиком за 2–3 вечера. Не стремитесь к 100 остановкам на старте — контент добавляется после релиза LiveOps-циклами.

### 5.4 Что проверяет валидатор (чек-лист скрипта)

- слово есть в эталонном словаре (после нормализации);
- слово составлено только из букв набора с учётом кратности (двух «А» в наборе нет — слова с двумя «А» отбраковка);
- длина 3–7 букв;
- не имя собственное;
- слова не повторяются внутри набора;
- нет корней из чёрного списка (нецензурная лексика) — список корней держите в отдельном файле и пополняйте;
- бонусные слова действительно встречаются реже (эмпирически: отсутствуют в топ-5000 частотного списка).

### 5.5 Формат `src/data/levels.json`

```json
{
  "mapId": "cities-vol1",
  "stops": [
    {
      "id": 1,
      "city": "Москва",
      "letters": "ВОКЗАЛТ",
      "words": ["ВАЛ", "ВОЛ", "ЗОВ", "ЗАЛ", "КОЛ", "АКТ", "ОТКАЗ", "ОТВАЛ", "ВОКАЛ", "..."],
      "bonus": ["ОТВАЛ", "ВОКАЛ"],
      "fact": "Столица России, первое упоминание — 1147 год."
    }
  ]
}
```

Объём: 30 остановок × ~22 слова ≈ 8–10 КБ JSON на карту — копейки для бандла, весь словарь на 5 карт уложится в несколько сотен КБ.

Если провал — меняем механику (размер набора, количество подсказок, темп), а не графику. Полировка невтяющего ядра — самая частая ошибка новичков.

### 6.3 Gate 2 (конец недели 8): «готово к модерации»

### 6.4 Gate 3 (конец недели 12): «что дальше?»

Критерии — таблица порогов в разделе 11. Три исхода:

- **Проход** → LiveOps-ритм (раздел 13), контент каждые 1–2 недели.
- **Частичный проход** → одна итерация правок (4 недели) по самой просевшей метрике, затем пересмотр. Не крутить дольше одного цикла.
- **Провал** → заморозить с письменными уроками (что сработало/нет, метрики). Вы прошли полный цикл за ~$30–40 — это дёшево купленный опыт для следующей идеи из анализа (например, когнитивные мини-игры для 55+).

## 9. Монетизация и лидерборды

### 9.1 Реклама: где и сколько (правила платформы учтены в П9)

| Формат | Где используется в «Словополе» | Лимиты |
|---|---|---|
| Interstitial | Переход «остановка пройдена → карта» | Максимум каждая вторая остановка, SDK платформы сам не даст чаще 1 раза в 60 секунд |
| Rewarded | Получение подсказки; удвоение очков остановки | Только по явному действию игрока, с честным диалогом перед показом |
| Sticky-баннер | **Не включать на MVP** | Крадёт экранное пространство при крупных шрифтах; вернуться к вопросу после метрик |

Железные правила модерации Яндекса: реклама никогда не показывается во время активного геймплея; отказ от rewarded не наказывается (не блокировать продолжение игры).

### 9.2 Внутренние покупки (минимальный набор)

| ID | Продукт | Тип | Цена (ориентир) |
|---|---|---|---|
| noads | «Убрать рекламу» | Непотребляемый | 199–299 ₽ |
| hints_5 | 5 подсказок | Потребляемый | 99 ₽ |
| hints_20 | 20 подсказок + бонус 5 | Потребляемый | 249–299 ₽ |

Технические требования: потребляемые товары консумируются после выдачи; статусы покупок синхронизируются при каждом старте (переустановка не должна терять noads); цены задаются в консоли Яндекса в YAN. Актуальные условия выплат и комиссию проверяйте в документации консоли — они периодически обновляются.

### 9.3 Реалистичные ожидания по деньгам

По бенчмаркам анализа (словесные/puzzle на Яндекс.Играх): RPM $0.35–0.55, ARPDAU $0.020–0.025. Арифметика:

## 10. Арт, шрифты, звук — минимальный путь

### 10.1 Принцип: art last

До Gate 1 игра обязана выглядеть «честно скучно»: чистые кнопки, кружки на карте, никаких иллюстраций. Арт — неделя 7–8, когда механика уже подтверждена.

### 10.2 Шрифты (это половина UX для 45+)

- Google Fonts с кириллицей, лицензия OFL: **Rubik**, **Nunito**, **Manrope** — выберите один для текста и один (или тот же, жирнее) для заголовков.
- Файлы woff2 бандлите в проект (внешние загрузки запрещены правилами площадки и убивают скорость старта).
- Базовый размер ≥18px, кнопки высотой ≥48px, контраст по WCAG AA. Проверяйте на телефоне бабушки/дедушки: яркость на минимум.

### 10.3 Графика

- Уровень v1: SVG-кружки остановок, пунктирный маршрут, CSS-градиент фона. Модерация это проходит — главное аккуратность.
- Бесплатные ассеты: **kenney.nl** (CC0 — можно без указания авторства), **game-icons.net** (CC-BY — нужна строка атрибуции в настройках игры).
- Картинка карты (если захочется тепла): бесплатные генераторы изображений; если лимитов не хватит — разовая покупка $5–10 вместо подписки.
- Иконка игры и обложка: требования по размерам смотрите прямо в форме загрузки файлов консоли — там актуальные спецификации.

### 10.4 Звук

- **freesound.org** с фильтром CC0, пакеты **Kenney Audio** (CC0).
- Хватит 6 звуков: тап по букве, слово верно, слово неверно, остановка пройдена, покупка, «Слово дня» готово.
- Обязательно: переключатель звука в настройках, remembered в прогрессе.

## Приложение А. Схема «сильная модель в браузере + дешёвые модели в OpenCode» (вариант за $0)

### А.1 Суть схемы и когда она уместна

Вместо платной подписки (раздел 3, Copilot Pro $10/мес) роль «одной сильной» модели может выполнять старшая GLM в браузере (chat.z.ai): там она бесплатна и принимает вложения-файлы. Сильная модель не трогает репозиторий — она думает: архитектура, декомпозиция на задачи, ревью диффов, разбор сложных багов. Всю механическую работу в коде выполняют бесплатные модели внутри OpenCode. Вы — маршрутизатор между двумя мирами.

Цена вопроса: $0/мес вместо $10 и примерно 15–20 минут в день на перенос контекста руками.

Когда уместна: первые 6–8 недель (весь MVP и Gate 1), пока кодовая база мала (до ~3–5 тыс. строк), а все решения всё равно проходят через вас. Когда вручную собирать контекст станет дороже, чем платить за подписку, — это и есть точка апгрейда (А.7).

### А.2 Распределение ролей

| Задача | Где решается | Почему |
|---|---|---|
| Архитектура, декомпозиция фичи на задачи | Браузер (GLM) | Нужны рассуждения и контекст, один раз в день |
| Ревью диффа за день, поиск логических ошибок | Браузер (GLM) | Дифф компактен, легко вставить целиком |
| Разбор сложного бага (непонятна причина) | Браузер (GLM) | Дешёвые модели «ходят кругами» на нетривиальных багах |
| Реализация задач по готовой спецификации | OpenCode (бесплатные) | Рутина: код по инструкции |
| Рефакторинг, тесты, мелкие фиксы, CSS | OpenCode (бесплатные) | Дёшево и быстро |
| Генерация словаря (промпты главы 6) | Браузер (GLM) | Креативная задача + ваш ручной контроль качества |

### А.3 Что передавать: артефакты, а не «простыни» кода

Главная ошибка схемы — копировать между окнами целые файлы. Передавайте артефакты.

Из OpenCode в браузер:
- `git diff HEAD~N..HEAD` за день/сессию — главный артефакт для ревью: компактный и самодостаточный;
- `git log --oneline` — список шагов;
- текст ошибки + 10–20 строк кода вокруг неё, если баг не поддаётся;
- вопросы одним списком (3–5 за раз), а не по одному — меньше ходок, меньше лимитов.

Из браузера в OpenCode:
- ответ сильной модели сохраняйте файлом `docs/plans/YYYY-MM-DD.md` (не вставляйте простыню в терминал);
- в OpenCode: «Прочитай docs/plans/2026-10-20.md и выполни задачу 2» — дешёвая модель работает по файлу и по правилам AGENTS.md, а не по буферу обмена.

Никогда не передавайте наружу: API-ключи, `idToken`, сейвы игроков, любые личные данные. Браузерный чат — внешняя сторона.

### А.4 Дневной протокол (≈15–20 минут накладных расходов)

**Утро, браузер, 10 минут.**
1. Два постоянных треда: «Планирование» и «Ревью» — не плодите новые, пусть копится контекст.
2. Первым сообщением прикрепляйте `docs/ai-context.md` (см. А.6) и AGENTS.md — так сильная модель будет писать инструкции в правилах вашего проекта.
3. Кратко: что сделано вчера, что по плану недели (раздел 6), где сомневаетесь. Получаете план дня, разбитый на задачи строго по шаблону А.5.
4. Сохраняете в `docs/plans/YYYY-MM-DD.md` и коммитите: `git add docs/plans && git commit -m "plan: <дата>"`.

**День, OpenCode — ваши обычные 10–20 часов в неделю.**
Цикл на каждую задачу: «Прочитай docs/plans/<дата>.md, задача N. Сначала покажи план правок — жду подтверждения» → правки → `npm run build` и тесты → коммит (одна задача — один коммит, раздел 4).

**Вечер, браузер, 5–10 минут.**

```bash
git log --oneline HEAD~5..HEAD
git diff HEAD~5..HEAD
```

Вывод вставьте в тред «Ревью» одним сообщением: «Ревью дня: [дифф]. Вопросы: 1) … 2) …». Получаете замечания и черновик завтрашнего плана; переносите их в `docs/ai-context.md` и закрываете день.

### А.5 Шаблон задачи (формат, в котором сильная модель отдаёт инструкции)

Требуйте этот формат строго: качество дешёвой модели почти целиком определяется качеством инструкции.

```markdown
## Задача 2: экран виртуальной клавиатуры
Файлы: src/components/Keyboard.tsx (новый), src/types.ts (добавить тип KeyDef)
Зависимости: задача 1 выполнена, коммит a1b2c3
Что сделать:
1. Ряды клавиш рендерятся из массива KeyDef, порядок задаётся словарём темы.
2. Тап по клавише вызывает insertLetter() из стора; стейт не мутируется напрямую.
Принять, если:
- npm run build зелёный, TypeScript strict без ошибок;
- клавиатура скрывается по кнопке ввода и по системной «назад».
Ограничения: новые зависимости не добавлять; стор не рефакторить.
```

Правило для сильной модели: она НЕ пишет финальный код (она не видит репозиторий) — она пишет спецификацию, по которой бесплатная модель в OpenCode напишет код.

### А.6 Файл docs/ai-context.md — «конституция» контекста

30–50 строк, обновляется по пятницам: стек и версии; структура папок; соглашения (нейминг, где живёт стейт, где тесты); текущий этап и дата; открытые вопросы и долги. Это первое вложение каждого утреннего сообщения — именно оно делает ответы сильной модели релевантными без длинных пересказов проекта.

### А.7 Ограничения схемы и точка апгрейда

1. **Лимиты браузерного доступа.** У старших моделей в chat.z.ai есть дневные ограничения (периодически меняются). Схема «2 захода по 10 минут» укладывается с запасом, а вот массовая генерация словаря (глава 6) может упереться в лимит — растягивайте её на 2–3 дня или переносите в API.
2. **Нет доступа к репозиторию.** Качество ответа = качество вложенного контекста. Забыли приложить файл — получите совет «в вакууме». Это главный риск схемы и главная причина дисциплины из А.3.
3. **Расхождение плана и кода.** Если дешёвая модель отступила от задачи, вечернее ревью по диффу это сразу покажет — не пропускайте вечерний заход.
4. **Точка апгрейда.** Когда почувствуете, что копируете больше, чем думаете (обычно после Gate 1), два пути: (а) Copilot Pro $10/мес из раздела 3; (б) GLM Coding Plan от Z.ai — он официально поддерживает OpenCode, включает GLM-5.3 и быстрый GLM-5.3-Flash, тарификация кредитная с лимитами на 5 часов и на неделю (от $18/мес). Протокол А.4 при этом не меняется — меняется только транспорт: планы и ревью начнут уходить из того же терминала, что и код.
